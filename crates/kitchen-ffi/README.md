# kitchen-ffi

A stable C interface to `kitchen-sim`, Hotdog Simulator's shared deterministic simulation, so that a client written in
another language (the Unreal client, `~/projects/hotdog-unreal`) links the very simulation the Bevy client and the
server run instead of rewriting it.

- `include/kitchen_sim.h`: the header, generated by cbindgen from `src/`. C with `extern "C"` guards for C++: opaque
  handles, plain structs, fixed-width integers, UTF-8 strings as pointer plus length. Its top comment documents the
  coordinate system, the units, the conversion to Unreal, the errors and the lifetimes.
- `libkitchen_ffi.a` (static, for Unreal) and `libkitchen_ffi.so`.
- `examples/smoke.cpp`: a C++ program that plays Kung Fu and Free For All bot matches through the header alone.

The crate is a package of its own (its own `Cargo.lock` and `target/`, as `crates/server` is). The repository has no
Cargo workspace, so nothing about the game's or the server's builds changes.

## Build

```sh
tools/build-ffi.sh                                   # release build + header (needs: cargo install cbindgen)
CARGO_TARGET_DIR=/some/dir tools/build-ffi.sh        # elsewhere; prints the .a's path last
crates/kitchen-ffi/examples/run-smoke.sh             # build, compile smoke.cpp with c++ (CXX=clang++ to choose), run it
cargo test --release --manifest-path crates/kitchen-ffi/Cargo.toml   # the Rust tests
```

Outputs: `<target>/release/libkitchen_ffi.a` and `libkitchen_ffi.so` (`<target>` is `crates/kitchen-ffi/target` unless
`CARGO_TARGET_DIR` says otherwise). Without cbindgen the script leaves the header as it is.

## Link

With the system compiler (what `run-smoke.sh` does):

```sh
c++ -std=c++17 -I crates/kitchen-ffi/include app.cpp libkitchen_ffi.a -lgcc_s -lutil -lrt -lpthread -lm -ldl -lc
```

Those are `rustc --print native-static-libs` for this library: the C library and its pieces, and `libgcc_s` for the
unwinder Rust's standard library is built with (panics are caught inside the library, but `_Unwind_*` must still link).
There is no C++ in the library and no reference to libstdc++ (`nm -u` shows only glibc's weak
`__cxa_thread_atexit_impl`).

### Into Unreal on Linux

Unreal builds with its own toolchain, not the system's: clang and libc++ under
`Engine/Extras/ThirdPartyNotUE/SDKs/HostLinux/Linux_x64/` (in ue6-main, `v26_clang-20.1.8-rockylinux8`), with a Rocky
Linux 8 sysroot whose glibc is 2.28. So:

- **Use the static library.** Its references to glibc are unversioned and bind when Unreal links, against the
  sysroot's glibc 2.28. The `.so` built on a newer system binds to that system's glibc (here 2.43) and would not load
  on an older one.
- **It must not need libstdc++, and it does not.** Rust's standard library is C, not C++; linking it beside Unreal's
  libc++ is fine. Checked: `examples/smoke.cpp` links with Unreal's own `clang++ --sysroot=<toolchain> -nostdinc++
  -isystem <toolchain>/include/c++/v1 ... -nostdlib++ libc++.a libc++abi.a -fuse-ld=lld` and the program needs nothing
  newer than `GLIBC_2.28`; it prints exactly what the system-compiler build prints.
- **The system libraries** (in the module's `Build.cs`):

  ```csharp
  // Source/HotdogSim/HotdogSim.Build.cs (a module of the Unreal project)
  string Ffi = Path.Combine(ModuleDirectory, "../../ThirdParty/kitchen-ffi");
  PublicIncludePaths.Add(Path.Combine(Ffi, "include"));
  if (Target.Platform == UnrealTargetPlatform.Linux)
  {
      PublicAdditionalLibraries.Add(Path.Combine(Ffi, "lib/Linux/libkitchen_ffi.a"));
      PublicSystemLibraries.AddRange(new string[] { "gcc_s", "util", "rt", "pthread", "m", "dl" });
  }
  ```

  Include the header inside `THIRD_PARTY_INCLUDES_START` / `THIRD_PARTY_INCLUDES_END` if warnings are errors.
- **One Rust staticlib per binary.** Two Rust static libraries in one Unreal binary each carry the Rust standard library
  and collide (`rust_eh_personality`, `__rust_*`). If a second Rust library is ever needed, build both into one.
- **Windows** is not done or tried here: the same crate should build a `.lib` with `--target x86_64-pc-windows-msvc`,
  linked with the system libraries `cargo rustc --release -- --print native-static-libs` lists on that target.

## The API

Every name is prefixed `ks_` / `Ks` / `KS_`. Every function that can fail returns a `KsStatus` (`KS_OK` = 0) and leaves
the reason in `ks_last_error()` (per thread). No panic crosses the boundary (`catch_unwind` round every entry point:
`KS_ERR_PANIC`, then destroy the handle). Handles are checked against the live ones before they are used, so null,
destroyed or made-up handles are refused, not followed.

**Lifecycle.** `ks_game_create(map_json, rules, seed, flags, &game)` makes an offline game: the map's JSON (as
`assets/maps/*.json`; empty for the bundled Counter Siege), the rules text (`""` for the map's own mode, `"mode=ffa"`,
`"mode=kungfu"`, `"mode=cards"`, `"sandbox ..."`: see `crates/kitchen-sim/src/rules.rs`), the seed of every draw (spawns,
shuffles, the Kung Fu bots' dice), and `KS_GAME_ALL_BOTS` (hotdog 1 is a bot too) / `KS_GAME_FOLLOW` (rounds follow by
themselves). `ks_client_create(&join, &game)` makes an online one. `ks_game_destroy(game)`. `ks_version()` (ABI,
protocol 12, tick and send rates), `ks_protocol()`.

**Offline play.** `ks_game_set_command(game, &command)` sets the local player's (hotdog 1's) input: the stick, yaw and
pitch, the `KS_BUTTON_*` bits, the weapon (Kung Fu: style + 1) and a pickup: the fields of the network command. Held
buttons persist until the next call; edges go once. `ks_game_step(game, dt)` applies it as the server applies a
person's command (in Kung Fu, `Feast::kungfu_command`) and steps the round: bots, physics, rules. Also
`ks_game_restart`, `ks_game_set_bot`, `ks_game_use_griddle`, `ks_game_ready` (Forts build phase), `ks_cards_command`
(Fully Loaded), `ks_game_set_tuning`.

**Online play.** Connect a WebSocket to `ws://HOST:8137/ws` yourself. `ks_client_poll` gives the join message first.
Feed everything the server sends to `ks_client_receive_text` (welcome, map, tuning, kungfu, cards, griddle, error,
snapshot) or `ks_client_receive_binary` (frames: decoded against the frame they name, checksummed, a whole frame asked
for when one does not check out). `ks_game_set_command` + `ks_game_step(dt)` make one numbered command a server step,
predict the local hotdog at once (except in Kung Fu) and queue batches with the acknowledgement. Send everything
`ks_client_poll` hands out, text as text frames and binary as binary frames. `ks_game_use_griddle`, `ks_game_ready`,
`ks_cards_command` and `ks_game_set_tuning` become the server's text messages; `ks_client_send_text` sends anything
else. `ks_client_status` tells the connection (welcomed, local hotdog, frames, corrections, the lobby's choice, the
server's last error). The readers below read this client's copy of the server's round.

**Reading.** Arrays are copied into the caller's: `(array, capacity, &count)` writes at most `capacity` and sets `count`
to how many there are (ask with capacity 0). Strings inside point into the game until its next mutating call.

| what | call |
| --- | --- |
| the round: mode, stage, clock, time left, goal, winner, wave, lobby countdown, alert, rules, map generation | `ks_game_match` |
| hotdogs: id, team, name, colour, feet, velocity, yaw, pitch, stance, HP, weapon, ammo, carry, score/kills/deaths, flags, last damage | `ks_game_players`, `ks_game_player`, `ks_game_local_player` |
| cats | `ks_game_enemies` |
| rounds in flight | `ks_game_projectiles` |
| loose objects: kind, state, holder, origin, quaternion, velocities | `ks_game_props`, `ks_prop_kind_name` |
| pickups, turrets, pests, emergence puddles, draped napkins, griddles | `ks_game_pickups`, `_turrets`, `_swarms`, `_puddles`, `_drapes`, `_griddles` |
| Forts: scores, field, bacon, stalemate, zones | `ks_game_forts` |
| Fully Loaded: the table as JSON | `ks_cards_json` |
| Kung Fu: per fighter style, move, time into it, phase, chi, guard, iron and the other flags; the fight's goal and end | `ks_kungfu_state`, `ks_kungfu_fighters` |
| Kung Fu's move table and numbers | `ks_kungfu_move_count`, `ks_kungfu_move`, `ks_kungfu_rules`, `ks_kungfu_style_name` |
| the static map: blocks, decks, ramps, sinks, scenery, starts, spawns, pickups, loose objects, zones; its JSON; the ground's height | `ks_map_info`, `ks_map_*`, `ks_map_json`, `ks_game_ground` |
| events: shots, splats, knocks, damage, kills, spawns, stage/round/winner, griddle flips, map changes, Kung Fu's moves and events | `ks_game_events` (drains), `ks_game_event_count` |
| the sound for an event | `KsEvent::sound`, `ks_sound_file`, `ks_sound_volume_at` |

## A client's frame

```c
// offline
ks_game_set_command(game, &input);
ks_game_step(game, dt);
ks_game_match(game, &match);            // if match.map_generation changed: read ks_map_* again
ks_game_players(game, players, 8, &n);  // ... props, projectiles, enemies, ks_kungfu_fighters ...
while (ks_game_events(game, events, 64, &n) == KS_OK && n > 0) { /* sounds, effects, feed */ }

// online: the same, with the socket round it
for (each message received) ks_client_receive_text / ks_client_receive_binary(game, data, len);
ks_game_set_command(game, &input);
ks_game_step(game, dt);
/* read and drain events as offline */
KsMessage m;
while (ks_client_poll(game, &m) == KS_OK && m.kind != KS_MESSAGE_NONE) send(m.kind == KS_MESSAGE_TEXT, m.data);
```

## Coordinates

The simulation's own, unconverted: metres, right-handed, Y up; the counter top is at y = 0.9025; a hotdog with yaw `a`
faces (-sin a, 0, -cos a). To Unreal (cm, Z up, left-handed): `UE = (-100 z, 100 x, 100 y)`, yaw `-a` in degrees,
pitch as is in degrees, quaternion `(qz, -qx, -qy, qw)`. The header's top comment has the details.

## Threads and determinism

A handle is not thread-safe: use it from one thread at a time (separate handles are independent). An offline game is
deterministic: the same map, rules, seed and commands give the same game (the tests check it, and the smoke program
prints the same thing built with the system's compiler and with Unreal's).
